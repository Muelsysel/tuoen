## Problem Statement

Windows 开发者想装一条工具链（JDK、Node、Python…），今天只能靠手工下载、手工解压、手工改 `PATH`。这套流程的失败模式全是静默的：

- 下载来源不可信或不可达时，你不知道自己拿到的是不是官方那份
- 解压出来的东西散落在随便挑的目录里，装第二个版本时只能覆盖第一个
- `PATH` 被反复手改，越改越长，直到某天整条失效
- 装完之后，"我到底装了什么、装在哪、哪个版本在生效"没有单一答案

而最要命的一点是：**这条工具链换到另一台机器上，今天没有任何办法搬过去。** 手工重来一遍的结果是一台环境与原来**不同**的机器——`PATH` 顺序不同、`PATH` 里的用户名不同、版本不同——而你不会立刻发现。

## Solution

`tuoen` 提供一条**可验证、可复现、不碰系统状态**的安装路径：

- **`tuoen install node@20.18.3`** —— 从上游官方源（或用户配置的镜像）下载，**校验 SHA256**，解压到 `versions/20.18.3/`，然后用**翻转 junction** 的方式把 `current` 指过去。
- **多版本共存**：`20.18.3` 和 `24.19.0` 同时存在，`tuoen use node@20.18.3` 只翻转一个 junction。
- **命令通过真 `.exe` shim 暴露**，不靠改 `PATH` 顺序（用户级条目在 `PATH` 上永远输给机器级条目）。
- **绝不使用 `setx` 写 `PATH`** —— 它会在 1024 字符处静默裁剪并永久展开 `%VAR%`。
- **镜像加速内建在下载层**：默认源优选 + 用户自定义镜像模板；**不托管任何二进制**，因此不承担再分发责任。
- **每个制品带可见的许可证字段**，并拒绝"不得收费 / 禁止再分发"条款的上游。

L0 是这一切的地基：没有它，后面的状态捕获、诊断、项目级 pin 都无从谈起。

## User Stories

1. 作为 Windows 开发者，我想用一条命令装一个精确版本的 Node，这样我不必再手工下载和解压。
2. 作为 Windows 开发者，我想让 `tuoen` 校验我下载的每个制品的 SHA256，这样我能确认拿到的就是官方那一份。
3. 作为 Windows 开发者，我想在下载失败时看到明确的原因（网络、镜像、哈希不符），而不是一个静默的坏安装。
4. 作为 Windows 开发者，我想同时装多个版本的同一个工具，这样我可以在不同项目间切换而不必卸载重装。
5. 作为 Windows 开发者，我想用 `tuoen use node@20` 切换当前生效的版本，并且这个操作是**原子的**——不能出现"切到一半"的状态。
6. 作为 Windows 开发者，我想在切换版本后**立刻**在同一个终端里用到新版本，不必重启终端。
7. 作为 Windows 开发者，我想让 `node`、`npm`、`python`、`java` 这些命令在**任何**终端里都能解析到我选的版本，包括 `cmd.exe`、PowerShell 和 IDE 的内置终端。
8. 作为 Windows 开发者，我不想为了装一个工具而同意 UAC 提权。
9. 作为 Windows 开发者，我想知道我的 `PATH` 是不是已经接近 8191 字符那个悬崖，因为一旦超过，**整条 `PATH` 会一次性全部失效**。
10. 作为 Windows 开发者，我想看到我装了什么、每个版本在哪、哪个在生效，输出要能一眼读懂。
11. 作为 Windows 开发者，我想 `tuoen uninstall` 干净地删掉一个版本，并在我删的是当前生效版本时明确警告我。
12. 作为中国大陆的开发者，我想让下载默认走国内镜像，这样我不必手动配代理或忍受超时。
13. 作为企业内网用户，我想配置自己的私有镜像模板，这样离线或受限网络下也能装。
14. 作为关注供应链的开发者，我想知道每个制品的许可证是什么，以及它是否允许再分发。
15. 作为关注供应链的开发者，我想在 `tuoen` 拒绝安装某个制品时知道**为什么**（例如"该版本不可再分发"），而不是一个通用错误。
16. 作为脚本编写者，我想用 `--json` 拿到**稳定、不本地化**的输出，这样我可以把它接进 CI 或自己的工具。
17. 作为中文用户，我想默认看到中文界面，但我**不**希望 `--json` 的字段名被翻译。
18. 作为脚本编写者，我想用 `--dry-run` 预览任何变更会做什么，且这个预览与真实执行走**同一套代码路径**（所以它不会骗我）。
19. 作为安全敏感的用户，我想知道 `tuoen` 拒绝解压某个归档的**具体原因**（路径穿越、保留设备名、绝对路径…），因为"解压失败"不足以让我判断这是上游问题还是攻击。
20. 作为用户，我想让 `tuoen` 在解压时正确处理超长路径，而不是在深层目录上神秘失败。
21. 作为用户，我想让 `tuoen` 正确处理含空格和版本号的安装路径（例如 `IntelliJ IDEA 2026.1.1`），因为这类路径在本机占 29%。
22. 作为用户，我想让 `tuoen` 的报错在中文系统上也能被我**和**脚本可靠识别，所以它必须基于错误码而不是本地化的错误文本。
23. 作为使用者，我想让 `tuoen` 在发现我的 `PATH` 上有条目遮蔽了它时明确告诉我，而不是让我以为工具坏了。
24. 作为使用者，我想在遮蔽发生时**自己**决定是否提权接管，而不是让工具静默改写我的系统状态。
25. 作为使用者，我想让 `tuoen` **绝不**改写 winget / Scoop 的 `PATH` 与状态。
26. 作为使用者，我想让 `tuoen` 能看到并**使用**我机器上已有的第三方安装（nvm4w 的 Node、官方安装器的 Python），而不是假装它们不存在。
27. 作为使用者，我想让 `tuoen` 在我要求卸载一个它**没有**安装的版本时拒绝，并告诉我为什么。
28. 作为维护者，我想让 `tuoen` 的核心逻辑不散落 `#[cfg(windows)]`，这样将来扩展平台是加一个 crate 而不是重写。
29. 作为维护者，我想让 shim 是一个极小的独立二进制，因为它在每次敲 `node` 的关键路径上。
30. 作为维护者，我想让所有变更走统一的 plan/diff/apply 引擎，这样不会有两套代码路径漂移。
31. 作为贡献者，我想让仓库结构一眼看懂（`core` / `platform` / `manifest` / `cli` / `shim` 各司其职）。
32. 作为贡献者，我想在修一个表格 bug 时不必理解整套 reparse point 机制。

## Implementation Decisions

**模块与职责**（Cargo workspace，见 `docs/DESIGN.md` 决策 29）：

- **`platform`** —— 平台 seam。**所有** Windows 相关的原始操作收在这里，业务逻辑不出现 `#[cfg(windows)]`：注册表读写、reparse point 创建与查询、`PATH` 读取（`DoNotExpandEnvironmentNames`）与写入（按值内容选择 `REG_EXPAND_SZ` / 保留原类型 / `REG_SZ`）、`WM_SETTINGCHANGE` 广播、错误码归一化。
- **`manifest`** —— catalog + recipe 两层 schema 与解析（决策 18）。catalog 描述"这是什么工具"（名字、别名、描述、**许可证**、上游项目、可用版本来源）；recipe 描述"这个版本怎么装"（URL 模板、校验、归档格式、解压布局、暴露方式）。**许可证挂在工具层，但分界按版本**（Oracle JDK 21+ 可镜像 / 8·11·17 不可）。
- **`core`** —— 引擎：下载、校验、解压、原子安装、junction 翻转、plan/diff/apply 生成。**不直接调用 Win32**，只通过 `platform`。
- **`cli`** —— `tuoen` 二进制：参数解析、人读输出（中文优先）、`--json` 稳定输出、退出码。
- **`shim`** —— 极小的命令转发器二进制。

> **实现期修正（票据 #4 / #5 / #6）：上面那张表少了三个 crate。**
> 落地时它们从 `core` 里分了出来，理由是每个都独立成了一个**可单独验证**的东西：
>
> - **`download`**（票据 #4）—— 源优选、镜像模板、SHA256、内容寻址缓存。分开是因为它
>   要能**单独跑真机探测**（`examples/fetch_probe.rs`）而不需要安装引擎存在。
> - **`archive`**（票据 #5）—— 三层 Zip Slip 防线 + 原子落位。这是全仓**最危险**的代码，
>   单独一个 crate 让它的威胁模型、上限、失败语义都只有一个地方可读。
> - **`store`**（票据 #6）—— 装在哪、谁装的、当前生效哪个版本。它是 `platform` 的
>   junction 原语与 `download`/`archive` 之间的接缝，也是**唯一**知道存储布局的地方。
>
> 依赖方向：`platform` → `manifest` → `download`/`archive` → `store` → `core` → `cli`。
> **没有反向边**（`platform` 不知道存储布局，`archive` 不知道 store 存在）。
>
> 另一处修正：原表把"下载、校验、解压、原子安装"都划给 `core`。实际上 `core` 现在
> 只剩**检测**（七层置信度），安装链路由 `cli` 直接编排 —— 因为 `core` 里放一个
> "安装服务"会让 `cli` 与它之间出现一层只做转发的空壳。等 L1 的 `capture`/`restore`
> 需要复用这条链路时再上提，那时它会有第二个调用方（**现在没有**）。

**存储布局（票据 #6 定下的契约，`tuoen-store` 是唯一知道它的地方）**：

```
%LOCALAPPDATA%\tuoen\store\
  <tool>\
    versions\
      <version>\              ← 载荷（payload），**与解压结果逐字节一致**
      <version>.json          ← 安装记录（来源、哈希、时间、布局）
      .staging-*\             ← `archive` 的临时目录，落位前短暂存在
    current  →  versions\<version>     ← **junction**，当前生效的那个
```

三条硬要求，每条都有理由：

1. **载荷目录里不许放我们自己的文件。** 记录是 `<version>.json` 而不是
   `<version>/tuoen.json`。理由不是洁癖：`layout.home` 会成为 `JAVA_HOME` 这类
   变量的值，而一个 JDK 的根目录里多出一个不认识的 JSON 是**某些工具真的会去扫**的东西。
2. **目录是事实来源，记录只是附加信息。** 记录缺失或坏掉时，版本照样出现在
   `tuoen list` 里（`record` 字段为空），只是说不出它从哪来。反过来，
   只有记录没有目录 = 没装。这样"用户手删了一个版本目录"是自愈的，
   而"记录文件被编辑器写坏了"不会让整个存储不可用。
3. **`.staging-*` 不是版本。** `archive` 的原子性来自"在同卷临时目录里解压完再一次
   `rename`"，所以 `versions/` 里**正常情况下**就会出现以 `.` 开头的临时目录。
   读存储时必须跳过它们 —— 否则用户会在列表里看到一个叫 `.staging-node-4831` 的版本。

**`install` 与 `use` 是两件事（`install` 不自动激活）**：`install` 只把版本放进存储，
`current` 一动不动；要生效得显式 `tuoen use`（或 `install --use`）。
理由见 `docs/DESIGN.md` 决策 49。代价是安装成功的输出**必须把下一步命令原样打出来**。

**关键接口约束**：

- **下载层是镜像加速的宿主，不是它的调用方**（决策 7）。源优选与用户自定义镜像模板从第一天就长在下载器里。
- **`--dry-run` 与真实执行共用同一套 plan 生成代码**（决策 20）。不得存在"预览版"与"执行版"两条路径。
- **所有变更产出可序列化的 plan**，步骤类型可枚举。
- **错误以码承载，不以文本承载**。面向用户的文本可以本地化，判断逻辑只能看码。

**必须遵守的硬约束**（违反前先读对应 ADR / 决策）：

- 绝不用 `setx` 写 `PATH`（决策与 ADR-0002 背景；1024 裁剪 + 永久展开 `%VAR%`）
- 绝不断言 symlink 可创建（ADR-0001）
- 只发 `.exe` shim，不发 `.cmd` / `.ps1`（ADR-0002）
- 绝不改写 winget / Scoop 的 `PATH` 与状态（决策 3）
- 第三方安装只读发现，不接管（ADR-0004）
- 相对路径永远受 `MAX_PATH`(260) 限制，`\\?\` 无法加前缀——**我们自己的解压/重命名代码必须用 `\\?\` 前缀**，并把 shell 集成视为永久 260 受限
- `--json` 输出稳定、不本地化（决策 35）

**解压安全**（Zip Slip 在本威胁模型里仍然活跃，见 CVE-2026-27800 / CVE-2026-28686 类问题）：先规范化再断言在根目录内；拒绝绝对路径、UNC、`..`；校验 symlink **条目目标**；拒绝保留设备名（`CON`/`PRN`/`AUX`/`NUL`/`COM1-9`/`LPT1-9`）；拒绝结尾的点和空格；拒绝名字里的 `:`（ADS 写原语）；大小写碰撞检测；大小与条目数上限。

**归档支持**：`.zip` / `.tar.gz` / `.tar.xz` / `.tar.zst` / `.tar.bz2` / **`.7z`** 全部走系统自带 `tar.exe`（bsdtar 3.8.8 / libarchive 3.8.8，含 libzstd + liblzma）。

> **修正（票据 #5 实测）**：本文件原写"`.7z` 是唯一需要内置库的缺口"。**那是错的。**
> libarchive 3.8.8 自己就认 7z —— 拿阿里镜像那份真的 `node-v24.19.0-win-x64.7z`
> （23,441,591 字节，SHA256 与上游 `SHASUMS256.txt` 一致）实测：`tar.exe -tf`
> 列出 2454 个条目、`-xf` 解出的 `node.exe` 能跑并报 `v24.19.0`。
> **不需要内置任何 7z 库。** 证据见 `research/BSDTAR_SAFETY_MEASURED.md` §3。

**许可证门禁**：制品带许可证字段；"不得收费 / 禁止再分发"的上游被拒绝安装并给出具体原因。**MSVC 建模为带外管理员前置条件，不是可管理包**（ADR 相关）。

**中文优先**：默认界面中文；**内置国内镜像**；中文文档优先；但 `--json` 的字段名与结构不翻译。

**外部参考**：实现遇到问题时第一参考对象是 **`mise`**（Rust、MIT、34.5k★）——尤其它的 Windows shim 处理、`PATH` 管理，以及 issue 区对已知 Windows 坑的记录。

## Testing Decisions

**好的测试只测外部行为，不测实现细节。** 对本项目尤其重要：内部有大量 Win32 交互和文件系统副作用，如果测试去断言"调用了哪个 API"或"创建了哪个临时文件"，它会随重构碎掉，且无法发现真正的回归。**测的是"用户能观察到什么"。**

**seams（按最高层优先，越少越好）**：

1. **CLI 进程边界 —— 主 seam。** 大部分测试通过运行 `tuoen` 二进制并断言 stdout/stderr/退出码/磁盘副作用来完成。这是最高层的 seam，覆盖参数解析、plan 生成、执行、输出格式的整条链路。**优先用它。**
2. **`core` 的 plan 生成 seam —— 第二条。** plan 是可序列化的纯数据，因此"给定这份机器状态与这个请求，应当产出什么 plan"可以在不起进程的情况下测。这是唯一值得新增的 seam，因为它让**变更逻辑**可测而不必真的改机器。
3. **`platform` 的适配器 seam —— 仅在不得不测平台差异时使用。** 例如"`PATH` 值不含 `%` 时应写 `REG_SZ`"。这类断言必须挂在适配器接口上，不能穿透到业务逻辑。

**测试环境要求**（这不是洁癖，是必要条件）：测试**不得**触碰真实的 `HKCU\Environment`、真实 `PATH` 或用户真实安装目录。需要一层可注入的根目录与注册表视图，让测试在临时目录 + 假注册表后端上跑。**否则测试会改开发者的机器。**

**要测的模块**：`manifest`（schema 解析与校验、许可证门禁）、`core`（plan 生成、解压安全、原子安装、junction 翻转的意图）、`cli`（`--json` 形状与稳定性、退出码、`--dry-run` 与真实执行的一致性）、`shim`（参数转发、退出码透传——这两个是最容易出隐蔽 bug 的地方）。

**已知的硬测试对象**（都是本机取证发现的真实场景，不是假想）：含空格且含版本号的路径；超长路径；`PATH` 值不含 `%` 时的类型选择；SHA256 不符；Zip Slip 的每一种变体；遮蔽检测。

**prior art**：仓库当前无代码，因此无既有测试可参考。**这一条要在第一个票据落地时补上**——先建立 CLI 进程 seam 的测试骨架，之后所有测试都沿用它的形状。

## Out of Scope

- **整机 dev-state 的捕获与还原**（决策 21/22）——招牌能力，但属 L1
- **环境体检诊断**（幽灵条目、`PATH` 重复与死条目、长度预算）——L1
- **项目级 pin**（`tuoen.toml`、`tuoen shell`、`tuoen trust`）——L1
- **全局包管理**（npm -g / pip 的捕获与还原）——L2
- **离线 bundle** —— L3
- **GUI** —— L3
- **`easyenv` 这个名字**——已废弃，项目名为 `tuoen`
- **跨平台**——V1 只发 Windows 二进制；本票据集只要求 seam 清晰，不要求支持其他平台
- **代码签名**——v0.1 有意未签名（ADR-0006）

## Further Notes

**上下文与依赖**：本 spec 的全部约束来自 [`docs/DESIGN.md`](docs/DESIGN.md)（35 条决策）、[`GLOSSARY.md`](GLOSSARY.md)（领域词汇）、以及 `docs/adr/0001`–`0006`。**违反其中任何一条之前先读它对应的理由**——本仓库里若干"本来很合理"的设计是被明确否决过的（`setx`、symlink、`.cmd` shim、接管第三方安装、自签名证书）。

**为什么 L0 值得单独一个 spec**：它的验收标准是"能真的装上一个工具并切版本"，而不是"框架搭好了"。**能编译但装不上东西不算完成。**

**一个必须如实对待的风险**：SignPath 要求项目"must already be released in the form that should be signed"，因此 **v0.1 必须未签名发布**，并附 `docs/UNSIGNED_BUILD.md` 里那份运行说明。这不是可选项，是签名路径的第一步。
