## 目标

把 `PATH` 当作**受管资源**来做 diff 与重建。这是"还原到新机器"里最容易出事的一步，也是调研判定"没人做过"的那个缺口。

**核心立场**：本机 `PATH` 已经是坏的（10 组重复、7 条失效、1 个拼错 3 次的目录、11 条硬编码用户名）。**"原样搬运"会把旧病一起移植**。所以这一票做的不是复制，而是**重建 + 逐条 diff + 选择性应用**。

## 必须实现的

### 1. `tuoen path diff <tuoen.d/path.toml>` —— 逐条 diff

对当前机器与目标快照的 `PATH` 做**逐条**比较，每条归入一类：

```
keep          两边都有，位置相同
add           目标有、本机没有
remove        本机有、目标没有
move          两边都有，但位置不同
fix           两边都有，但本机这条是坏的（不存在 / 重复 / 空 / 用户名依赖）
case-only     仅大小写不同（Windows 上同一个目录，但字符串不同）
```

每条输出必须带**理由**（为什么判成这一类），以及来源快照里的 `owner` / `reparse` / `has_username`。

### 2. 重建（rebuild）—— 产出**新的有序列表**，不是打补丁

重建规则（必须实现且可配置）：

- **去重**（忽略大小写）—— 保留**首次**出现的位置，后续重复标记为 `remove`
- **去掉失效条目** —— 但**默认不静默删**：失效条目归入 `fix`，由用户选择是否移除
- **修复拼写** —— 不做自动纠错（危险）；但**必须能识别并报告**像 `C:\Software\tool` vs `C:\Software\tools` 这种"疑似拼写错误"（本机在两个 hive 里错了 3 次，从未生效过）
- **重写用户名依赖** —— `C:\Users\<旧名>\...` → 当前用户名，**且必须显式报告重写了哪几条**（本机 11 条，其中 2 条在机器级）
- **保留顺序语义** —— 机器级在前、用户级在后是平台事实，不可改变；重建只作用于**各自 scope 内部**的顺序
- **长度预算** —— 重建后必须检查 8191 悬崖并告警（复用 `path.length-budget`）

### 3. 选择性应用

用户必须能：
- 按类别选（如只 `add`，不 `remove`）
- 按条目选（交互式多选或 `--pick <index>`）
- **预览后放弃** —— 放弃时不留任何副作用

### 4. 写入实现（复用 L0 的 platform 层）

- **绝不使用 `setx`** —— 文档写 1024 字符上限且内容是"被裁剪后应用"（静默数据丢失），且操作已存在的值会**永久展开所有 `%VAR%` 引用**。本机算术：用户 725 + 机器 978 = 1704 字符，`setx PATH "%PATH%;..."` 会**既裁剪又把整条机器 PATH 永久复制进 HKCU**
- 直接写 `HKCU\Environment`：**值含 `%` 才用 `REG_EXPAND_SZ`，否则保留原类型，再否则 `REG_SZ`**
- 读取用 `DoNotExpandEnvironmentNames`
- 写后广播 `SendMessageTimeoutW(HWND_BROADCAST, WM_SETTINGCHANGE=0x1a, 0, L"Environment", SMTO_ABORTIFHUNG=2, 5000, &out)`
- **机器级写入需要提权** → 不静默提权，产出 `requires-elevation` 待办项（决策 12）

### 5. `--dry-run` 走同一套代码路径

预览与执行**必须**共用 diff/重建代码（决策 20）。两套代码路径必然漂移，而**漂移的预览比没有预览更危险**。

### 6. 可见性说明

环境块在 `CreateProcess` 时复制 → **只有 Explorer 及其之后新起的子进程**能拿到。已在运行的 cmd / PowerShell / VS Code / IDE / 服务 / 计划任务都拿不到，**我们自己的进程也拿不到**（除非显式打补丁）。
写入后必须打印这句话：**"请重启终端"是平台限制，不是工具不友好**。

## 明确不做

- **不自动清理失效条目**（只归类为 `fix` 由用户选）
- 不做拼写自动纠错（只报告疑似）
- 不接管第三方版本管理器的 `PATH` 条目（nvm4w 的 `C:\nvm4w\nodejs` 只作为 `owner = third-party` 参与 diff，**不改写它**）
- 不实现完整的 `restore`（那是下一票）—— 本票的出口是 `path diff` 与 `path apply`

## 测试 seam 与硬性约束

**两层 seam 都用**：

1. **`core` 的 plan 生成 seam** —— diff / 重建是**纯函数**（输入两个 `path.toml`，输出 diff + 新列表），**必须在这里密集单测**。它分支最多，是这一票的主要风险。
2. **CLI 进程边界** —— `--dry-run` 的输出与真实执行的副作用。

**硬性约束（违反即为 bug）**：

- **测试不得读写真实的 `HKCU\Environment` / `HKLM` / 真实 `PATH`。** 注册表必须走假后端。
- 测试不得访问真实网络。
- **不得在测试里真的改开发机的 `PATH`** —— 这是本仓库最容易造成真实伤害的一步。

**必须有的用例**：

- 六种 diff 类别（`keep` / `add` / `remove` / `move` / `fix` / `case-only`）各一个
- **仅大小写差异**必须判为 `case-only` 而不是"一个 add + 一个 remove"
- 去重保留**首次**位置（构造 `A;B;A` → 保留第一个 A）
- 空条目：`;;`、开头、结尾各一个
- 8191 边界：**1719 / 8190 / 8191 / 8192**，断言重建后的检查行为
- 用户名重写：机器级与用户级各一条，且断言**报告了重写清单**
- 拼写错误识别：`C:\Software\tool` vs 存在 `C:\Software\tools` → 报告为疑似
- **选择性应用**：只选 `add` → 断言 `remove` 类条目**未被改动**
- **放弃预览 → 零副作用**（断言假后端未被写）
- `--dry-run` 与真实执行的 diff **逐条相同**（这是决策 20 的直接断言）

## 验收标准

- `cargo test --workspace` 全绿，clippy `-D warnings` 干净
- **在作者本机上真实跑一次 `tuoen path diff`**（用 `capture` 产出的 `path.toml` 作为目标），把完整 diff 贴进 issue 评论，并与取证报告对照（预期：10 组重复、7 条失效、`C:\Software\tool` 拼写错误、11 条用户名依赖）
- **证明 `--dry-run` 未产生副作用**（前后各贴一次 `HKCU\Environment\Path` 的字符数与哈希）
- 贴出"选择性应用"的一次真实演示（只应用 `add` 类）

## 写入范围（advisory）

- `crates/core/`（diff / 重建的纯函数）
- `crates/platform/`（注册表写、广播 —— 若 L0 未覆盖则补齐）
- `crates/cli/`（`path diff` / `path apply` 子命令）
- `tests/`、`fixtures/`

**不要动**：`crates/manifest/`、`crates/shim/`
