## 目标

**这一票写的是证据，不是功能。**

在作者本机上跑一次完整的 L1 端到端流程，把真实结果记录下来。**所有产出必须是真实命令的真实输出**——不得有任何编造、推测或"预期应该是"。

## 必须做的事

### 1. 完整走一遍

```
capture → doctor → path diff → restore --dry-run → restore → restore（第二次，验幂等）
```

每一步的**完整输出**贴进本 issue 评论。

### 2. 必须给出的具体证据

| 证据 | 要求 |
|---|---|
| `capture` 的 `tuoen.d/` 产出 | 贴出 `path.toml` 的 `[budget]` 段与重复条目计数 |
| `doctor` 的完整输出 | 逐条与取证报告对照 |
| `path diff` 的完整输出 | 逐条与取证报告对照 |
| `restore --dry-run` 的 plan | 用本机自己 capture 出的快照 |
| **`--dry-run` 与真实执行的对比** | **真的对比过**，逐条列出差异（预期为空） |
| **未使用 `setx`** | 代码审查 + 证明（如 `grep -r setx` 无命中） |
| **未触碰 nvm4w** | 前后各贴一次：`NVM_HOME` / `NVM_SYMLINK` 的值、`C:\nvm4w\nodejs` 的 junction 目标、`settings.txt` 的哈希 |
| `HKCU\Environment\Path` 的变化 | 前后各贴一次字符数与哈希 |
| 幂等 | 第二次 `restore` 的输出（预期"无变更"） |
| `manual_actions` | 真实输出，确认 `credential-reconfigure` **只含意图不含材料** |

### 3. 发现的问题各自成为新 issue

任何不符合预期的行为 → **新建 issue**，不要在这一票里顺手改代码。
新 issue 里写清楚：现象、复现命令、真实输出、预期行为、以及是 bug 还是取证有误。

### 4. 实测数据写进评论

- 安装耗时（若这一票真的装了工具）
- `capture` / `doctor` / `path diff` 的耗时
- `PATH` 长度变化
- shim 启动开销（若 L0 的 shim 已可用）

## 硬性约束

- **不得为了让结果好看而修改代码。** 如果某个检查项没命中本机的已知问题，**如实记录**并说明是"检查项不灵敏"还是"取证有误"。
- **不得编造任何输出。** 所有贴出的内容必须是终端里的真实文本。
- **不得触碰 nvm4w 的符号链接 / 环境变量 / `settings.txt`。**
- 如果这一票真的装了工具（如 Temurin JDK 或 Node），**只能装到 `tuoen` 自己的目录**，不得覆盖任何现有安装。
- 还原 `PATH` 时**必须先用 `--dry-run` 看过**，且**必须先证明可以恢复**（备份 `HKCU\Environment\Path` 的原始值到文件，并贴出恢复命令）。

## 验收标准

- 上面表格里的每一项都有真实证据
- 发现的每个问题都有对应的新 issue
- 本 issue 的评论里有一份**诚实的结论**：L1 的四个能力（捕获 / 诊断 / PATH 重建 / 还原）**哪些真的能用、哪些还有洞**
- 若结论是"还不能用"，**这一票依然算完成** —— 如实记录本身就是它的产出
