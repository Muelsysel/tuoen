# ADR-0004: 第三方安装只读发现，不接管

**状态**: 已接受（2026-10-02）
**来源**: `docs/DESIGN.md` 决策 3、13

## 背景

本机上真正在用的工具链**几乎都不是我们装的**：
```
node     → nvm4w 装的（C:\Users\Muelsyse\AppData\Local\nvm\v24.19.0 + 一个符号链接）
python   → 官方安装器装的（Python312）
JDK8/17  → 手工解压的（C:\Dev\base\JDK\）
```
若只捕获/管理"我们自己装的"，**这个功能在作者本机上几乎是空的**。

同时用户在更早的决策里已经选定：**只读检测 winget/Scoop，绝不改写它们的 `PATH` 与状态**（决策 3）。

## 决策

**只读发现第三方安装：可见、可选中、可 pin、可使用；但 `uninstall` 不去动它们。**

## 后果

- 工具链列表反映机器的**真实**状态，而不是我们的私有目录。
- **"采纳" ≠ "接管"**。接管会改写 nvm4w 那个**需要管理员才能重建的符号链接**及其环境变量，**违反决策 3**；而且实操上会打架——`nvm use 20.18.3` 会继续重写那个符号链接，**两个版本管理器争抢同一个 reparse point**。这不是理论风险，是装完第二天就会发生的 bug。
- 每个条目必须**标注来源与置信度**（决策 25）：`JDK17（手工解压于 C:\Dev\base\JDK\JDK17，未由 tuoen 管理）`。
- 调研把 **"采纳既有安装而不是重装"列为第 4 名差异化**：nvm-windows 的 README 直接叫用户先把 Node 卸了；Chocolatey 把等价能力做成**付费**的 Package Synchronizer。

## 被否决的方案

- **不采纳**：工具在作者自己机器上看不见最常用的东西。
- **接管并迁移**：违反决策 3，且出错无法挽回（那个符号链接非提权修不回来）。

## 参考

本机是"双重管理腐坏"的活证据：`NVM_HOME` 与 `NVM_SYMLINK` **同时存在于 `HKCU\Environment` 和 `HKLM\Session Manager\Environment`**。
