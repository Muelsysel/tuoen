# ADR-0003: 所有变更走统一的 plan / diff / apply

**状态**: 已接受（2026-10-02）
**来源**: `docs/DESIGN.md` 决策 20、28

## 背景

用户已决定 `PATH` 重建采用"重建 + diff 预览 + 选择性应用"（决策 28）。问题是：**这个机制只给 `PATH`，还是给所有变更？**

## 决策

**统一引擎。安装、卸载、切版本、`PATH` 编辑、还原，全部先产出 plan；`--dry-run` 走同一套代码路径。**

## 后果

- **最大的一次变更也有预览**。如果只有 `PATH` 能预览，那么"还原到新机器"（几十个安装 + 环境变量 + 配置文件）反而没有预览——而它恰恰是最需要预览的一次操作。
- **只有一套代码路径**。两套（预览版和真做版）必然漂移，而**漂移的预览比没有预览更危险**——用户会基于错误信息做决定。
- 让"选择性应用"在格式层面天然成立：配合决策 22（状态文件用目录 `tuoen.d/` 分文件），"只应用 PATH 部分"就是选一个文件。
- 工程代价：所有变更操作必须被建模为可序列化的 plan 步骤，不能有"顺手改一下"的捷径。

## 为什么这是差异化而非工程洁癖

调研把 **"机器可读的整机 dev-state 模型，双向，带 `plan → diff → apply`"列为第一名差异化**，依据是：

- `winget` 官方明确放弃了排序（winget#4940 原话："will not likely be able to resolve sequencing dependencies in the short term"）
- `scoop export` 只导应用
- `chezmoi` 管文件不管机器
- `winget export` 对无法匹配项只给**警告**

## 被否决的方案

- **只有破坏性操作走 plan**：安装/卸载直接做。问题是"还原到新机器"的主体正是安装，把它排除等于没做。
- **只有 `PATH` 走 plan**：最小改动，但放弃了本项目的招牌能力。
