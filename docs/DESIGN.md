# tuoen · 拓境 — 设计规格

> **拓境 — 让你的 Windows 开发环境可搬运、可复现。**
> *Tuoen — capture, carry, and rebuild your Windows dev environment.*

本文件是**已达成共识的设计决策的固化**。每一条都来自与项目所有者的逐轮评审（`grilling` 工作流），
并尽量以本机取证或上游文档作为依据。**凡未经确认的推断都显式标注。**

---

## 0. 一句话定位

**整机开发状态（dev-state）的捕获与还原器**，而非又一个包安装器。

理由：按名字安装包、项目级 pin、shim 机制已被商品化（调研记录 6 个活跃 + 2 个已死的多语言版本管理器，
其中 `mise` 为 34.5k★ 的 Rust 项目）。而**"整机 dev-state 的捕获/还原"无人占据**——
`winget export` 只导包 ID 并对无法匹配项给警告；`scoop export` 只导应用；
`chezmoi` 管文件不管机器；`winget` 官方明确放弃了排序（winget#4940）。

**差异化排序**（据调研，仅前四项进入 V1 范围）：

1. 机器可读的整机 dev-state 模型，双向，`plan → diff → apply`
2. 提权作为一等资源来规划（逐项 scope、一次同意、明确的非管理员降级路径）
3. PATH 作为受管资源（所有者、顺序、长度预算、重复与死条目检测、声明式移除）
4. 采纳既有安装而不是重装

**中文优先**与上述定位互补：最痛的人群正是国内网络环境 + 需在内网/离线机器上重建开发环境的人，
而 `mise` 的 `bootstrap` 系统资源是 Linux/macOS 形状的。

## 1. 决策日志

### 1.1 定位与范围

| # | 决策 | 结论 | 关键理由 |
|---|---|---|---|
| 1 | 工具身份 | **完整包管理器**，自建 manifest 体系与安装引擎；winget 仅作可能的 manifest 来源，**不是执行后端** | 走"编排器"路线则"换电脑"的还原保真度上限 = winget 能否复现精确版本，无法承诺 lock 级重建 |
| 2 | 技术栈 | **Rust** | 决定性理由是分发与自举：管理 Node/Python 的工具若要求先装 Node 是逻辑循环；产出单个 `.exe` |
| 3 | 与 winget/Scoop 的边界 | **检测但隔离**：只读检测，**绝不改写它们的 PATH 与状态** | 改写会制造"两个包管理器互相破坏"的 bug，而这类 bug 会被算到我们头上 |
| 4 | 招牌功能 | **整机 dev-state 的捕获与还原** | 见 §0 |
| 5 | 平台范围 | **Windows 优先，在 I/O 与平台 API 处留清晰 seam**；V1 只发 Windows 二进制 | 留 seam 本身是好模块设计，成本极低；**不等于** V1 跨平台 |
| 6 | 默认语言 | **中文优先**：默认中文界面 + 内置国内镜像 + 中文文档优先 | 见 §0 |
| 7 | 落地顺序 | L0 地基 → L1 可用 → L2 扩展 → L3 重资产；**镜像加速提前进 L0** | 镜像加速不是"功能"而是**下载层的属性**，事后往写死的下载器里塞源优选代价高得多 |
| 8 | 名称 | **`tuoen` / 拓境**；tagline：**拓境 — 让你的 Windows 开发环境可搬运、可复现** | 造词，不表意，故 tagline 承担全部定位信息 |

### 1.2 功能清单

V1 全做，分四层：

- **L0 地基** — manifest schema + 解析 + 下载/校验/解压 + 原子安装 + junction 翻转 + `install`/`list`/`uninstall`；**镜像加速（源优选）内建在下载层**
- **L1 可用** — 多版本共存 + 项目级 pin（`shell`/`trust`）+ **整机状态捕获与还原** + 体检诊断
- **L2 扩展** — 全局包管理（npm -g / pip）
- **L3 重资产** — 离线 bundle + GUI

### 1.3 安装与版本机制

| # | 决策 | 结论 | 关键理由 |
|---|---|---|---|
| 9 | 版本切换 | **Junction 优先，symlink 作为可选** | 本机实测：Developer Mode 关闭 + 未提权时 `New-Item -ItemType SymbolicLink` 文件与目录**都失败**，而 `New-Item -ItemType Junction` **成功**；微软文档明确 `SYMBOLIC_LINK_FLAG_ALLOW_UNPRIVILEGED_CREATE`(0x2) **只在 Developer Mode 已开启时有效**，传 flag 不是绕路方案 |
| 10 | 命令暴露 | **自建真 `.exe` shim**，**只发 `.exe`，不发 `.cmd`/`.ps1`** | ① 用户级工具在 PATH 上永远排在机器级条目之后（实测：进程 PATH 首条为机器条目），只能靠 shim 抢名字；② `.cmd` shim 在 Node ≥18.20.2/20.12.2/21.7.3 之后**无法被 spawn**（CVE-2024-27980，nodejs/node#52681） |
| 11 | shim 版本解析 | **生成时写死目标路径** | 因为用 junction 翻转，shim 指向稳定的 `.../current/<tool>.exe`，**切版本根本不碰 shim**，只改 junction 目标。省掉每次调用的配置读取与解析（实测原生 shim 33–36ms vs C# 86ms，差距正在此处） |
| 12 | 提权策略 | **默认用户级；提供可选提权的机器级安装** | 检测到机器级条目遮蔽我们的 shim 时，明确告知"这 N 个条目遮蔽了我们"，用户可选择提权接管。**绝不静默改写系统状态**（与决策 3 一致） |
| 13 | 第三方安装 | **只读发现，不接管** | 能看见、能选中、能 pin、能使用；但 `uninstall` 不会去动它们。理由：接管 nvm4w 意味着改写它那个**需要管理员才能重建的符号链接**，且两个版本管理器会争抢同一个 reparse point |

### 1.4 项目级 pin

| # | 决策 | 结论 | 关键理由 |
|---|---|---|---|
| 14 | 声明方式 | **单文件 `tuoen.toml`** | 管的是**一整条互相约束的工具链**（JDK+Node+Python 版本相互约束），分开声明会漂移 |
| 15 | 生效方式 | `tuoen shell` 永远可用；**自动切换需 `tuoen trust` 一次** | 进入陌生仓库就自动改工具链版本是安全漏洞（恶意仓库可 pin 一个带后门的"Node 版本"） |
| 16 | 信任记录 | **用户级中央清单**（`%APPDATA%\tuoen\trust.toml`），记录绝对路径 + **首次信任时的指纹** | 信任标记若放在被信任的目录内，任何 clone 下来就自带信任标记，等于没有机制；指纹是因为路径可能被替换（删目录再 clone 同名目录） |
| 17 | 企业策略 | 信任清单**格式设计成未来可被系统级策略覆盖** | 个人用户不需要提权，但企业需要统一管控 |

### 1.5 数据与状态模型

| # | 决策 | 结论 | 关键理由 |
|---|---|---|---|
| 18 | manifest schema | **两层：catalog（工具元数据）+ recipe（版本安装步骤）** | 许可证字段必须挂在"工具"层，但 Oracle 的规则**按版本分界**（JDK 21+ 为 NFTC 可镜像；JDK 8/11/17 不可再分发），两层的切分点正好落在"版本"上 |
| 19 | 包目录来源 | **内置种子目录 + 可选远程签名索引** | 全内置则每次上游发版都要跟着发版；全远程则无网络用户什么都装不了（与"离线包"自相矛盾）。先例：Python 3.14 官方安装器即 `index.json` + Authenticode 签名目录 + `requires_signature` |
| 20 | 变更引擎 | **统一 plan/diff/apply**，所有变更都先产出 plan，`--dry-run` 走同一套代码路径 | 若只有 PATH 能预览，则最大的一次变更（还原到新机器）反而没有预览；且两套代码路径必然漂移，**漂移的预览比没有预览更危险** |
| 21 | 状态边界 | 捕获：我们管理的安装 + 检测到的第三方安装 + 环境变量 + PATH 结构 + 配置文件 + WSL/.vsconfig + 全局包清单，**逐项标注来源与置信度**；排除：缓存、**密钥材料**、项目代码、系统组件、进程噪声 | 只捕获自己装的 → 在作者本机上这个功能几乎是空的（node 是 nvm4w 装的、Python 是官方装的、JDK 是手工解压的） |
| 22 | 状态文件 | **目录 `tuoen.d/` 分文件**（tools / path / env / configs / wsl …） | "PATH 变了"与"Java 版本变了"是两个独立 diff；也让"只应用 PATH 部分"这种选择性操作在格式层面天然成立 |
| 23 | 密钥策略 | **主动扫描 + 排除 + 报告跳过清单** | 仅靠敏感路径黑名单会漏（作者本机的 `.m2/settings.xml` 不在任何黑名单里却藏着活 PAT）。原则：**捕获"意图清单"（版本/路径/名字），绝不捕获"材料"（密钥/token/密文）** |
| 24 | 幽灵条目 | **只报告，破坏性动作留给用户显式触发** | "自动清理注册表和 PATH"出错即无法挽回，而检测本身也可能误判（如把网络驱动器上的真实安装当幽灵） |
| 25 | 检测信任层级 | **分层报告 + 标注来源与置信度** | 把"PATH 上确认可执行"与"注册表声称已装但文件缺失"并列展示，会让用户看一眼就不再信任这个工具 |
| 26 | 全局包管理 | **捕获还原 + 按 Node 版本隔离** | 本机陷阱：全局 npm 包装进了 `C:\nvm4w\nodejs` 符号链接内部，**切 Node 版本会静默"丢失"它们**；只做捕获还原则清单会与实际状态脱节而用户不会察觉 |
| 27 | 全局包前缀 | **环境变量重定向**（`NPM_CONFIG_PREFIX` 及 pip 等价物），不写用户配置文件 | 写 `.npmrc` 会覆盖用户自己的配置；且 pnpm 曾因仓库本地 `.npmrc` 展开 `${ENV}` 导致密钥外泄而不得不停止该行为 |
| 28 | PATH 重建 | **重建 + diff 预览 + 选择性应用** | 本机 PATH 已是坏的（10 组重复、7 条失效、1 个重复 3 次的拼写错误、11 条硬编码用户名）。"原样搬运"会把旧病一起移植 |

### 1.6 工程与发布

| # | 决策 | 结论 | 关键理由 |
|---|---|---|---|
| 29 | 仓库结构 | **Cargo workspace 多 crate**（`core` / `platform` / `manifest` / `cli` / `gui` / `shim`） | shim 是每次敲 `node` 都要跑的程序，必须独立成极小二进制，不能把 GUI 的依赖图拖进启动路径；跨平台 seam 需要独立 `platform` crate 才不被业务逻辑渗透 |
| 30 | GUI 框架 | **Tauri v2** | Tauri 的 GUI 进程本身是 Rust 二进制，官方文档允许 `src-tauri/` 作为 **Rust workspace 成员** → CLI 与 GUI 共用同一套类型，schema 一改两边一起报错。Electron 则要求为每个 Rust struct 永久维护 TypeScript 镜像 |
| 31 | 许可证 | **MIT OR Apache-2.0 双许可** | Rust 生态事实标准；同时给出 MIT 的简洁与 Apache 的显式专利授权 |
| 32 | 离线 bundle | **元数据 + 厂商 URL + 哈希清单**；自包含归档**只装许可允许再分发的**（Temurin / CPython / Node.js） | Oracle JDK 8/11/17 不可再分发、MSVC 完全不可再分发；"再分发别人的安装器"是这类项目最容易踩的坑 |
| 33 | 命名一致性 | `tuoen.toml` / `tuoen.lock` / `tuoen.d/` / `%APPDATA%\tuoen` / 环境变量前缀 `TUOEN_` | 一致性 |
| 34 | 镜像加速边界 | **源优选 + 用户自定义镜像模板**，**不托管任何二进制** | 不托管二进制意味着不承担再分发责任，这是自建引擎能安全落地的前提；自定义模板同时覆盖"企业内网"与"离线包"两类需求 |
| 35 | 输出稳定性 | **`--json` 输出必须稳定、不本地化** | 否则脚本化与未来的 GUI 会被中文界面绑死 |

### 1.7 L0/L1 实现期新增（决策 36–59）

这二十四条是**实现过程中被真机输出逼出来**的，不是设计阶段想到的。其中 36–38 已经过项目所有者拍板。

| # | 决策 | 结论 | 关键理由 |
|---|---|---|---|
| 36 | 检测的置信度层级 | **七层**：`managed` / `executable` / `registered` / `manager-owned` / `directory-only` / `registered-missing` / `alias-ghost` | **`registered` 是必需的第七层**：ARP 的 `InstallLocation` 常常是一个**目录**（本机 `C:\Program Files\Git\`、`C:\Program Files\Java\jre1.8.0_491\`、`C:\Program Files\WSL Dashboard\`），且它**不在 `PATH` 上**。把它报成 `executable` 违反 `executable` 自己的判据（"在 `PATH` 上能解析到、文件真实存在且大小 > 0" —— 三条一条都不满足）。它与 `directory-only` 的区别是**有注册表记录**（因此可重建），与 `registered-missing` 的区别是**目录真的在**（所以不是幽灵） |
| 37 | 报告粒度 | **每个工具一行，只报主命令** | 按命令报会让 `node` 变成 4 行、四个不同版本号并列（`node.exe 24.19.0` / `npm.cmd 11.17.0` / `npx.cmd 11.17.0` / `corepack.cmd 0.35.0`），用户没法回答"我的 Node 是哪个版本"。次要命令（`javac` / `npm` / `pip` / `uvx`）**仍然被发现**（shim 需要知道它们在哪）并参与遮蔽判定，只是不单独占行 |
| 38 | 持久环境变量的注册表路径 | 用户级是 `HKCU\Environment`，机器级是 `HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Environment` —— **两者都不在 `SOFTWARE` 下面** | 这条是**用一条真 bug 换来的**：`RegHive::Hkcu` 会给不带绝对前缀的子键自动拼 `SOFTWARE\`，于是"读用户级环境变量"实际去读 `HKCU\SOFTWARE\Environment`（不存在），**静默返回空表**。症状是"不报错、只是少了一半数据"，比报错危险得多 —— 见 `docs/acceptance/L1-01-detect.md` §6.1 |
| 39 | HTTP 传输 | **shell out 到系统 `curl.exe`**（Schannel 后端），**不打包 TLS 栈** | ①Windows 10 1803+ 自带 `curl 8.21.0`（Schannel + zlib + HTTP/2 + `--location` / `--connect-timeout` / `--fail-with-body` / `--proxy` 全都有）；②项目已经信任系统 `tar.exe` 做解压，同一条理由；③**Schannel 直接用 Windows 证书存储 → 企业 TLS 拦截的根证书自动被信任**，而打包 rustls + webpki-roots 在内网里必然连不上；④避免把 ~40 个 crate 的依赖图引进一个必需品。传输层在 `Transport` trait 后面，将来换纯 Rust 实现不影响上层 |
| 40 | 镜像选源 | **内置顺序只是默认值，真实的选源靠探测**：`tuoen fetch --probe-sources` 对候选源发 range GET 实测，把可达性与耗时排序并缓存 | **实测逼出来的**：本机对这个网络探测，`mirrors.tuna.tsinghua.edu.cn` 与 `mirrors.ustc.edu.cn` **全部不可用**，`mirrors.aliyun.com/adoptium` **404**（目录结构不同），而 `cdn.npmmirror.com` 94ms、`mirrors.cloud.tencent.com` 267ms、`nodejs.org` 280ms、`api.adoptium.net` 327ms 都可用。"抄一份国内镜像 URL 清单"的做法在这里会直接失效 —— 清单本身不是可用性。**探测目标有三条硬要求**（每条都是真机换来的）：①**必须是文件不能是目录** —— 不认区间请求的服务器会把 `-r 0-0` 当普通 GET，目标是目录时本机实测下了 **155794 字节**的版本列表（"为了问一句能不能到"）；②**不能带版本号** —— 镜像会剪枝旧版本，那时探测会把一个能用的源判成不可用；③**必须与镜像前缀分开** —— 否则阿里源会被自己的探测淘汰（它的制品前缀目录 404 而制品完全正常）。三条合起来给出的目标是 `<mirror_prefix>index.json`。**判决稳定但状态码不稳定**：同一个 URL 跨运行出现过 403 / 200+整份列举 / 404，所以分类只能到 `source-unavailable` 一层，不能基于状态码写"这个镜像坏了"的判断 |
| 41 | SHA-256 | **自实现，不加 `sha2` crate** | 理由不是"省一个依赖"，而是**这段代码的位置**：它站在"我们信任这个字节流"与"我们把它解压到磁盘"之间，是整个工具里最该被独立核对的一段。它是 FIPS 180-4 的固定算法（无版本演进、无平台差异、无配置项），纯函数、约 120 行、零依赖零 IO，**且有官方测试向量** —— "对不对"不靠信任，靠跑。**代价是真实的**：本区间在这段代码上修了四个独立缺陷（`finish` 的填充公式在 `total + 1 > 56` 时 `u64` 下溢；`finish` 从来没压缩最终块 —— "总长是 64 的整数倍"不等于"缓冲是空的"；`update` 的尾巴被替换而不是追加，所以**逐字节喂与一次喂结果不同**；`update` 里 `bytes` 没重新切片，多用原始长度算了一次块数）。**教训**：我曾在这里放了一条 `debug_assert_eq!(self.buffered, 0)`，它让一个**正确**的实现看起来是坏的，排查代价是一整轮 —— **错的是断言，不是代码**；一条错误的断言比没有断言更贵 |

| 57 | 启动开销报**增量**，而且**先证明转发是真的、再计时** | `startup_probe` 在计时之前先做两件器材自检：shim → `--sleep 400` 的实际耗时必须 ≥ 400 ms（证明确实在等），以及经过 shim 的 stdout 与直接跑**逐字节一致**（证明转发没坏） | 第一版没有自检，量出了一个**不可能**的数字：经过 shim 的 `node --version` 比直接跑还**快 17 ms**。一个转发器不可能让它转发的东西变快，所以那一定是"shim 根本没在转发"—— 而正是这条自检追出了决策 54 那个常量折叠 bug。**一条不能失败的测量不是测量。** 口径也要说清：参考值「Scoop 原生 shim 33–36 ms」是**总量**，不能拿来和增量比。本机实测（release，40 轮取中位，前 6 轮预热）：`argdump --noop` 直接 5.6 → 经 shim 16.3；`node.exe --version` 直接 23.1 → 经 shim 33.3，**增量约 9–11 ms**（内含一次 `CreateProcessW` + 一次 `WaitForSingleObject` + 我们自己这个进程的启动，后者由 `argdump --noop` 的约 5 ms 给出地板）。进一步压缩需要 `no_main` 手工入口，**V1 不做** |
| 58 | 会启动进程的探针与测试，三条铁律 | 写进 `AGENTS.md`：①**绝不允许任何程序启动它自己**；②**构造命令行只留一个函数，参数必须拼在结尾的 NUL 之前**；③**跑之前算最坏进程数，给它上限，跑完清场核对** | 两次事故，两次都不是"逻辑写错"而是代价不对称。第一次是决策 55 的自指 shim（20580 个进程）。第二次是 Ctrl-C 探针的宿主"fork 自己"进入子模式：`wide()` 已经带了 NUL 结尾而参数被拼在了那个 NUL **后面**，于是子进程收到**零个参数**、回到宿主模式又 fork 一次 —— **409 个进程**，每个还带着一个不可见控制台和继承来的 stdout 管道（管道不关，调用方就永远不返回）。现在的结构里没有任何程序会启动自己：宿主起执行者、执行者起被测程序，宿主在动手之前还会断言"执行者不是我"。**同类危险的第三条**：前缀参数里混进 U+0000 会把命令行在那里截断，目标带着比预期少的参数启动**且不报错** —— `ShimSpec::validate` 现在直接拒掉它 |
| 59 | shim 的测试要**在 release 下再跑一遍** | 验收脚本里同时跑 `cargo test --workspace` 与 `cargo test --release -p tuoen-shim` | 直接由决策 54 推出：常量折叠只在 LTO 打开时发生，而 `cargo test` 默认是 debug —— 也就是说**当时那 43 条全绿的测试，对那个 bug 一条都没有约束力**。"测试通过了"这句话的分量取决于测试跑在哪个 profile 下，而这一点在报告里通常会消失 |

### 1.8 L0-08 实现期新增（决策 60–71）

票据 #8 把 `tuoen` 第一次接到**真的会改用户系统状态**的地方（`HKCU\Environment` 的 `Path`），所以这一节的中心题目是「怎么在证据上把危险操作围住」。

| # | 决策 | 结论 | 关键理由 |
|---|---|---|---|
| 60 | `PATH` 模块的形状是 `analyze`（只读）→ `plan_*`（产出计划）→ `apply`（写 + 广播） | `plan_add` / `plan_remove` 与 `apply` 分开；`run(action, dry_run)` 是便捷组合，`dry_run` 时走**同一套** `plan_*` 只是不调 `apply` | "`--dry-run` 走同一套代码路径"不是一句实现风格，它是**这条验收唯一能成立的方式**：另写一条只读分支的话，dry-run 通过只能证明那条分支对，证明不了真正落盘的路径对。验收里钉这件事的办法是断言 `run(dry_run=true)` 与 `run(dry_run=false)` 产出**同一个 `PathPlan`**（`assert_eq!(real_plan, plan)`） |
| 61 | 预算档位按**生效的** `PATH` 算，不是按某一个作用域 | `PathBudget::of(effective_chars, registry_chars)`；`effective_chars` = 进程里那一条的长度，`registry_chars` = 机器级 + 用户级原文之和 | `cmd.exe` 看的是进程环境块里那一条，而它是"机器级 + 用户级 + 进程注入"拼起来的。本机实测：注册表 1780、进程里 **2107**，差的 **327** 字符是 6 条进程注入（`%LOCALAPPDATA%\Microsoft\WindowsApps` 的 MSIX 别名、cargo 的 `target\debug`、rustup 的 lib 目录…）。只看注册表会**少报 327 字符**，也就是在一个已经很危险的机器上给出一个偏乐观的告警 |
| 62 | `PathPlan::budget_after` 是**注册表口径的下界**，并且这一点写在字段文档里 | 计划里只算得出"机器级 + 用户级写回后"的长度，进程注入那部分无从得知 | 一个缺失的数比一个错的数更危险 —— 所以不去猜：字段文档明写"真实的生效长度**只会更长**，只会比它更早撞悬崖"。`PathPlan` 是给人和 CLI 看的，一个偏乐观的数字会被当成安全边际 |
| 63 | 读 `PATH` **不展开** `%VAR%`（低层走 `RegEnumValueW`），并且含 `%` 的条目**不判"失效"** | `RealEnvBlock` 同时保留 `value_raw` 与 `value_expanded`；`analyze` 对含 `%` 的条目跳过失效判定 | 展开是**不可逆的信息损失**：`setx` 事故的典型残留正是"值里字面含有 `%VAR%` 但类型不是 `EXPAND_SZ`"，只有不展开读才区分得出"本来就是这样"与"被展开过"。而"含 `%` 的条目是不是失效"我们**答不了**（我们没展开它），答不了的题不许猜 —— 报成失效就是假阳性，用户会去删一条其实好的路径。代价（决策 71 的第 7 条）是 `%NOPE%\bin` 这种真坏的条目我们不会报 |
| 64 | 写只写**用户级**；一次写完整条值；计划与现状一致时**不写也不广播** | `apply` 只在 `plan.will_write()` 时调 `Registry::set_value`，然后才广播；`plan_remove` 撞上自己的 shim 目录直接返回 `NoopReason::ProtectedShimDir` | 机器级要提权，而"顺手提权"会让一个装工具的命令变成 UAC 弹窗 —— 不做，也不假装能做。**逐段改**会有中间状态，而中间状态就是"`PATH` 暂时少了几个目录"（另一个进程正好在这时启动就拿到坏环境）—— 所以整条一次写完。**广播是全局副作用**（`HWND_BROADCAST` 打到每一个顶层窗口），"用户跑了一次命令"不构成发它的理由，所以只有真写了才发 |
| 65 | 空条目在**分析**里保留，在**计划**里显式丢弃并报告条数 | `parse_entries` 保留空段（`ScopedPath::empty_positions` 报出位置）；`plan_*` 过滤它们并产出 `PathChange::DropEmptySegments { count }` | 本机机器级 `Path` 里**真的有** `;;`（下标 21 是一条空条目）。解析时吃掉它，会让"我们是不是改过用户的 `PATH`"这件事失去证据（写回时它自己消失了，而输出里看不到）；报告成一条明确的改动，用户才知道我们动了什么。`;` 在 `PATH` 里本来也没有语义，攒着只是垃圾 |
| 66 | 参数里含 `;` 的目录**当场拒绝**，不是拆分、也不是加引号 | `plan_add` / `plan_remove` 返回 `PlatformError::Unsupported`；CLI 映射成稳定 slug 后非零退出 | `PATH` 用 `;` 分隔，而**引号救不了它**（Windows 解析 `PATH` 时不看引号 —— `"C:\a;b"` 里的分号照样分隔）。写进去之后**再也分不出**原来是一条还是两条，而用户看到的是"我加了一个目录，结果多了两个"。这是一种"输入本身就是错的"状态，唯一诚实的处理是拒绝 |
| 67 | 重复检测用**规范化**后的键（大小写折叠 + 去掉多余结尾反斜杠，保留 `C:\` 这种根） | `PathEntry::key()`；`normalize_entry` 的注释里写明"只去多余的那一个" | 真机上与一个**独立的** PowerShell 分组实现交叉核对：按原文分组找到 10 组，我们的实现找到 **12** 组，差的 2 组只差一个结尾反斜杠（`C:\Program Files\dotnet` vs `…\dotnet\`、`C:\Program Files\MySQL\…\bin` vs `…\bin\`）。顺着这条，`C:\Software\tool\` 也被并进 `C:\Software\tool` 那组（×2 → ×3）。**两条实现的分歧全部由这个已知差异解释**，没有第三类 |
| 68 | 遮蔽检测按**生效顺序**（机器级在前、用户级在后），对每条命令取**第一个**命中它的目录；shim 目录不存在就一条都不报 | `detect_shadowing`：先列 `<shim_dir>/*.exe` 得到我们发布的命令集合，再按 `PATH_EXTENSIONS`（`exe/com/bat/cmd/ps1`，按 Windows 的解析顺序）逐个目录查；每个目录**只列一次**（`BTreeMap` 缓存） | 遮蔽是一个**顺序**问题，不是一个"有没有"问题：同样的两个目录换个顺序结论就相反。按作用域分头判断会得出错误答案（用户级排在机器级后面）。shim 目录不存在时我们一条命令也没发布，"遮蔽"没有主语 —— 报 0 才是对的（本机现在就是这个状态，见验收文档 §5） |
| 69 | `plan_add` **不需要** `shim_dir`；只有 `plan_remove` 需要 | 两个函数的签名故意不对称，并在 `plan_add` 的文档里写明理由 | 加目录是**追加在末尾**：已经在前面的条目优先级不变，所以我们（以及任何现有条目）都还在前面 —— **加目录永远不可能遮蔽我们自己的 shim**。于是"保护 shim 目录"这件事只对删除有意义（删掉自己的 shim 目录 = 把刚装好的命令从 `PATH` 上摘掉）。第一版给 `plan_add` 也留了这个参数并且写了一句 `let _ = shim_dir;` —— 一个被忽略的参数比一个不对称的签名更坏：它看起来像有保护，其实没有 |
| 70 | 测试策略：`platform` 层用假注册表全覆盖；CLI 的进程边界测试**只碰只读与 `--dry-run`**；真机写入只由探针做，**且只写别的值名**；**不给出厂二进制留"假注册表"后门** | `crates/platform/tests/path_contract.rs` 26 条全部走 `FakeRegistry`；CLI 测试断言 `--dry-run` 前后 `show --json` 逐字节相同；探针写 `TUOEN_PATH_PROBE` | 票据第 ⑨ 条（"测试不得触碰真实 `HKCU\Environment`，否则测试会改开发者的机器"）有两条路：给真实现做可注入，或者给出厂二进制加一个环境变量后门。**后者被否决**：那是一个随发布版一起发出去的后门，误设（或者被别的程序设）就会把用户的 `PATH` 写进一个 JSON 文件 —— 用一个"测试方便"换一个"用户可能踩"的开关，代价不对等。真机证据改由**探针 + 探针的自证**提供 |
| 71 | 真机探针必须**自证它没碰 `Path`**，并把这个结论写进机器可读的契约行 | 探针在开始与结束各快照两个作用域的 `Path`（类型 + 原文），`before == after` 必须为真 → `SUMMARY … path_untouched=1`；验收脚本**另外**用 `GetValue(..., DoNotExpandEnvironmentNames)` 独立做一遍同样的比对 | 这是"一趟危险的探针"能不能被信任的分界线。一个只写 `TUOEN_PATH_PROBE` 的探针**声称**自己不碰 `Path`，与它**证明**自己不碰 `Path`，是两件事；而这份证据还必须能被机器检查（否则它只是文档里的一句话）。两套**独立实现**（我们的 `Registry::value` 与 PowerShell 的 `GetValue`）得出同一结论，才排得掉"我们的读法本身就错了"。同一条道理用在探针的其它自检上：`checks_failed=0` / `probe_residue=0` 都进契约行，验收脚本逐项解析 —— 而验收脚本自己用 `-SelfTest` 证明**退出码真的会跟随失败数**（决策 50） |

### 1.9 L0-08 的生效顺序与"遮蔽只能报告"（决策 72–74）

这三条是**真机实测把一次"看起来对"的实现推翻**之后补的，都关于同一个对象：
`PATH` 的**顺序**到底是谁决定的。

| # | 决策 | 结论 | 关键理由 |
|---|---|---|---|
| 72 | 生效顺序以**进程里那一条 `PATH`** 为准；注册表里有、进程里没有的条目**追加在末尾** | `PathAnalysis.effective: Vec<EntryRef>`（每条带出处 scope + 下标）；`analyze` 从 `process.path_entries()` 建这个序列，再补上注册表里没出现在进程里的那些 | 第一版把"生效顺序"实现成"机器级 + 用户级"，而这是**不完整的**：`CreateProcess` 复制的是**父进程的环境块**，注册表只在 shell 建立环境时被读一次。真实形状是 `[启动器注入] + 机器级 + 用户级`，本机实测排在最前面的是 PowerShell 的 MSIX 别名目录 —— **它排在机器级前面**，也就是说"机器级永远在前"这句话本身也需要限定。`cargo` / `rustup` / 宿主又各自往前面插自己的目录（本机一次 `cargo run` 里数出 6 条注入）。**必须同时保留注册表那一侧**：本机实测这个终端的环境块里缺两条注册表条目的原因是"**它开得比我加那两条更早**"（`C:\Program Files\GitHub CLI\` 与 MinGW 的 `bin`）—— 那是平台事实（§2.2），不是数据错误；把它们丢掉会让遮蔽判定在一个陈旧的终端里**漏报**。**顺带确认了一条设计依据**：机器级条目确实全部排在用户级条目之前（实测：进程 `PATH` 去掉首条 MSIX 之后前 31 条与"机器级 + 用户级"逐条一致），ADR-0002"用户级工具永远输掉名字冲突、只能靠 shim 抢名字"成立 |
| 73 | **遮蔽只能报告，不能自动修** —— 用户级 shim 目录**永远**赢不过机器级同名条目 | `tuoen path add <shim 目录>` 之后必须**重新分析并报告残余遮蔽**，指出**具体是哪一条**（作用域 + 目录 + 文件名）以及可执行的下一步；绝不改机器级 | 这一条是**顺序决定的**，不是实现限制：进程 `PATH` 里机器级整体排在用户级之前，而 `plan_add` 只能写用户级（机器级要提权，本项目不做"顺手提权"）。于是本机那个 `C:\nvm4w\nodejs`（机器级第 18 条）**无论怎么调整用户级顺序都赢不了**。真机实测：往我们的 shim 目录里放一个空的 `node.exe`，分析就报出 `node` 被 `C:\nvm4w\nodejs` 遮蔽；放一个 `java.exe`，报出被 `C:\Program Files (x86)\Common Files\Oracle\Java\java8path` 遮蔽 —— **正好是票据 ⑥ 点名的两个例子**。假装能自动修，就是在给用户一个"装好了"的错觉 |
| 74 | `plan_add` **只追加、不提供 prepend**；`plan_remove` 才需要 `shim_dir` 保护 | `plan_add(block, dir)` 与 `plan_remove(block, dir, shim_dir)` 的签名故意不对称，理由写在函数文档里 | 追加在末尾**永远不会遮蔽任何人**（已有的条目优先级不变），所以加目录不需要保护 shim 目录。而"prepend 抢到前面"这个功能**解决不了它看起来要解决的问题**：机器级条目仍然在前面（决策 73），于是它只会在机器上没有同名条目时生效 —— 而那种情况下追加本来也能生效。一个在关键场景里无效、在无关场景里多余的开关，代价是让人以为问题已经处理了 |

### 1.10 L0-08 的真机端到端：遮蔽报告、分母与"不对称必须说出来"（决策 75–78）

这四条来自**第一次在真机上把整条 L0 链跑通**（下载 → 归档 → store → junction → shim → `PATH`）。
节点是：真实 store 里已装 `node 24.19.0`，于是 `tuoen shim add node` 真的生成了 4 条 shim，
`tuoen path add <shims> --dry-run` 真的报出 4 条全被 `C:\nvm4w\nodejs` 抢了。

| # | 决策 | 结论 | 关键理由 |
|---|---|---|---|
| 75 | 遮蔽报告的**分母**必须是一等数据：`shim_commands`（我们的 shim 目录里发布了哪些命令） | `PathAnalysis.shim_commands: Vec<String>` → `path show --json` 的 `shimCommands`、`path.plan` 的 `shimCommands` | `shadowed_shim_count == 0` 有**两个成因完全相反**的解释："我们的命令都赢了"和"我们一条命令都还没发布"。原来的判据只看 `shadowed_shims.is_empty()`，于是本机空目录（我们一个 shim 都还没装）也会被报成"每条命令都是第一个被命中的"—— **一句假话**。有了分母，空目录说的是"没得比"。**同类教训**：`path.plan` 的 `shimDir: null`（没查）与 `shadowedShims: []`（查了没输）也必须分得开 |
| 76 | `path add` / `remove` 之后**必须**印残余遮蔽报告，且按作用域给出可执行的下一步 | `PathPlanView::with_shadowing(&analysis, shim_dir)` —— 落盘**之后重新分析**（拿计划之前那次分析是在报告一个已经不存在的世界）；只在"真被抢了"或"这次加的就是我们自己的 shim 目录"时印（给不相干的目录加 `PATH` 时那是噪声） | 决策 73 说"只能报告不能自动修"，这一条是它的**落地形状**：报告得晚（用户已经以为装完了）就等于没报。真机效果是逐条点名 `node` / `npm` / `npx` / `corepack` 各自被哪个目录、哪个文件抢了；机器级那条只能手动改，报告就直接这么说，并给出用户级的 `tuoen path remove <那条>` |
| 77 | `shim add`（**工具**）与 `shim remove`（**命令名**）的粒度不对称**必须显式说出来** | `ShimRemoveView.siblings_left` / `tool_id` → 人类输出给出**可以直接抄**的 `tuoen shim remove corepack npm npx`；`core::tool_for_command` / `command_names` 提供反查 | 实测抓出来的：`shim add node` 生成 4 条，而 `shim remove node` **只删 `node.exe`**（`remove` 收的是命令名），盘上还剩 3 条 —— **静默的半途状态**。不对称本身是对的（`remove npm` 必须能只删 npm），错的是不说。"漏下的兄弟"的判据必须包含"**盘上真的还在**"：只按表推断的话，删一个从没生成过全集的工具会报出一堆不存在的文件 |
| 78 | 测试断言**不许依赖机器状态**（"真实的 X 目录不存在"这类），只能断言"跑完前后没变" | `real_home_listing()` 顶层 + **往 `shims` 里看一层**；两条 `the_real_tuoen_home_was_not_touched_by_this_files_tests` 改成只比较前后 | 这是决策 50 的**第二次**教训，代价换了个方向：那次是"断言不会失败"（假的通过），这次是"断言会被误报"（假的红）。原断言是"真实的 shim 目录不存在"—— 那是**机器状态**，不是被测代码的性质：任何人真的用过 `tuoen shim add` 都有这个目录，本票的真机验收就把它踩红了。而只列顶层同样不行："在真实 shim 目录里写了一个 shim"这种最严重的事故看不见，因为 `shims` 这个名字本来就在那儿 —— 所以必须往里看一层，再比前后 |

### 1.11 L0-09 真机验收：怎么证明"新终端里生效了"（决策 79–83）

### 1.12 L1-12 捕获：`tuoen.d/` 的格式与"说不准"怎么写下来（决策 84–90）

票据 #12 的产物是**磁盘上的文件**，而文件是契约。这一节记的是格式与判据定下来的规矩；
每一条的理由都比"更整齐"具体。

| # | 决策 | 结论 | 关键理由 |
|---|---|---|---|
| 84 | `tuoen.d/` 里**多一个 `skipped.toml`**（票据的骨架里没有它），而且它是**跨 section 的同一个文件** | 六个文件：`schema.toml` / `tools.toml` / `path.toml` / `env.toml` / `wsl.toml` / `skipped.toml`。`--only path` 只产出 `schema.toml` + `path.toml`（没扫环境变量就没有"跳过了什么"可言，凭空写一个空清单会让"这份快照不完整"看起来像"没有东西被跳过"） | "跳过了什么、为什么"是**跨 section 的一句话**（本票扫环境变量，票据 #17 扫配置文件），而用户问的是"这份快照是不是完整的"—— 那个问题只有一个答案。放在一个文件里，加一个新 section 的跳过项**不需要动任何已有文件的结构**，这正是票据对后续票的要求 |
| 85 | "在不在"是**三态字符串** `yes` / `no` / `unknown`，不是布尔 | `Existence` 与 `TargetExistence`（后者多一个 `not-a-path`）。票据给的骨架是 `exists = true` | 布尔会**合并两个相反的结论**：`PATH` 上的 `%NOPE%\bin`，我们**故意不展开**用户环境变量（规矩二），所以对它只能答"不知道"。写成 `exists = false` 是在说"我们看过了，它不在"—— 而我们没看过，也不打算猜。同理 `UV_PYTHON=3.13` 不是"指向的目录不存在"，它是**不是路径** |
| 86 | `expanded` 的含义是"**Windows 会把它解析成什么**"，所以由**注册表类型**决定：`sz` 的值不展开，`expand-sz` 才展开；展开由我们自己算，**不用 `ExpandEnvironmentStringsW`** | 进程注入条目（没有类型）按原样。查找顺序：机器级 → 用户级 → 进程（后者覆盖前者）。**认不出来的 `%NAME%` 原样保留**，于是它自然落进 `Existence::Unknown` | 对一个 `REG_SZ` 里字面含 `%VAR%` 的条目做展开，会把它显示成一个**根本不存在的路径** —— 而那种条目正是 `setx` 事故的残留形状，恰恰是最需要被如实报告的东西。不用系统函数是因为它看的是**当前进程**的环境块，而我们要回答的是"**这台机器上**会被解析成什么"：真机上两者几乎一样，在固定装置里差了十万八千里，而固定装置才是这条逻辑被测试的地方 |
| 87 | `path.toml` 里**另有一份 `[[effective]]`**：真实解析顺序的一串 `{scope, index}` 引用 | 不变量：每一条都能在 `[[entry]]` 里找到对应行（有专门的用例） | 作用域内的顺序加上"机器级在前、用户级在后"这条规则**推不出**真实的生效顺序 —— 启动器还会在最前面注入条目（本机实测有 PowerShell 的 MSIX 别名，77 字符，不在任何注册表里）。只存 `[[entry]]` 等于把"第 0 条是谁"这件事丢掉 |
| 88 | `owner` 的判据**只有三条**，`unknown` 是默认值而不是失败 | 落在我们自己的根里 → `tuoen`；落在 `%SystemRoot%` 里 → `system`；本身是 reparse point（别人的版本切换器）→ `third-party`；其余 → `unknown`。为了让 core 能拿 `&dyn` 的适配器直接调 `analyze()`，给它的三个泛型加了 `?Sized` | **宁可说不知道，也不猜一个目录归谁。** 猜错会让还原时动到别人的东西。被砍掉的那条候选判据是"按已检测到的工具的路径前缀归属"—— 它要再跑一次检测（**再 spawn 一遍进程**），而这一票有专门的用例钉住"探测只经过注入的运行器"，那条用例会因为这种"顺手再来一次"而变红 |
| 89 | 跳过记录里**不许出现值的任何字节**（连前几位、长度、哈希都不行）；判据分两类 | ①**值的形状**（`glpat-` / `ghp_` / `xox…` / `AKIA` / `npm_` / `AIza` / `sk-` / JWT / 私钥正文 / Stripe）；②**名字像凭据**（整段比较 `TOKEN` / `SECRET` / `PASSWORD` / `PAT` / …）**且过三个护栏**：值 ≥ 20 字符、不像路径、不是布尔数字 | `tuoen.d/` 的用途就是**被提交进仓库**，所以"不小心把前 8 位放进跳过记录"是最容易发生的一种泄露 —— 它看起来已经很小心了。三个护栏各自对应一个真实反例：`TOKENIZERS_PARALLELISM=false`（名字命中但是布尔）、`SSH_KEY_PATH=C:\…`（值是路径，密钥在文件里）、`API_KEY=`（空值）。**`PAT` 必须按整段比较**：`PATH` 里含有这三个字母，而它恰好是最不该被跳过的变量 |
| 90 | 幂等的**时间戳由调用方传进来**（`CaptureOptions::captured_at`），于是"两次逐字节相同"可以被直接断言；`without_timestamp` 只用于比对**真实输出** | 同一台机器、同一个时间戳 → 渲染结果逐字节相同（固定装置里的用例）；真实两次跑的差异**只允许**出现在时间戳那一行（`without_timestamp` 按行首删 `captured_at` / `"capturedAt"`，不做反序列化） | 反序列化会顺手抹掉"我们写出去的到底是什么字节"这个信息，而幂等要求的正是字节。把时间戳变成输入而不是 `now()`，幂等性就从"忽略某个字段之后相同"升级成"完全相同"—— **能被直接断言的性质比能被绕过的性质更不容易悄悄坏掉** |

### 1.13 L1-12 真机验收：三个"假结论"是怎么来的（决策 91–94）

真机验收（`docs/acceptance/L1-12-capture.md`）抓出来的都不是崩溃，而是**看起来完全合理的错话**。
四条规矩，各自对应一个当场发生的例子。

| # | 决策 | 结论 | 关键理由 |
|---|---|---|---|
| 91 | **空条目不是一个目录**：`;;` 那种空段落的 `exists` 恒为 `unknown` 且**不问磁盘**，形状记在 `empty` 字段上 | 判"失效条目"的判据是 `!empty && exists == "no"`，不是 `exists == "no"` | 真机 HKLM 的 `Path` 第 21 段是空的。第一版让空串走正常分支，磁盘对 `""` 答"不存在"，于是 8 条 `no` 里有 1 条是它 —— 而"这里缺一个目录"与"这里本来就什么都没有"是两件事。**`doctor`（#13）照 `exists == no` 数就会多报一条永远修不好的坏条目**：一个永远修不好的发现会训练用户忽略所有发现 |
| 92 | 一个字段的语义**只以票据的定义为准**：实现与自己的文档互相自洽，不等于与票据一致 | `dup_index` 是"**同值条目里的序号**"（0 = 首次出现），所以从没重复过的值恒为 0、`dup_index > 0` 的行数**就是**重复条目的条数 | 实现做成了"不同的值依次编号"（`A B C C D → 0 1 2 2 3`），模块文档也照这个写了一遍 —— 两处一致、都好看，**但真机会印 32 而不是 18**。三条平行定义（票据、代码、注释）里只有票据算数。同类风险：任何"我按更好理解的方式实现并写进文档"的时刻 |
| 93 | "**不是一条路径**"的判据必须覆盖**列表**：`;` 分隔的值（`Path` / `PSModulePath`）不是一条路径，`target` 也不记 | `is_a_list(value) = value.contains(';')`，**排在"像不像绝对路径"前面**；四态里它落 `not-a-path` | `Path` 与 `PSModulePath` 的第一个字符就是 `C`，只判前缀会把**整条 `;` 串**拿去问磁盘，答案恒为"不存在"。真机上 4 条 `target_exists = "no"` 里有 3 条是这么来的，而"`Path` 指向的目录不存在"是一句会直接误导 `doctor` 的假话；修完剩的那 1 条（`HALCONROOT` → 已卸载的 HALCON）才是真的发现。**判据写在文档里但没写进代码，等于没写** |
| 94 | **检查自己写错枚举拼法会造出一个假的差异**，而它与"代码错了"长得一模一样 | 核对 `reparse` 分布时用 `^reparse = "symlink"$`，真机上是 `symlink-dir` → 差一点把"采集器没认出 nvm4w 的符号链接"报出去 | 这是决策 50、78 的第三次同类教训：50 是"断言不会失败"（假通过），78 是"断言会被误报"（假的红），94 是"**核对本身用错了口径**"。共同点：**验收的每一句话都要能被独立复核**，包括验收脚本自己写的那几句 —— 所以 `scripts/acceptance-L1-12.ps1` 里每一条数字都要与脚本自己从注册表/磁盘数出来的那一份对照，而不是与 `tuoen` 自己的输出对照 |

### 1.14 L1-13 体检：事实与判断分开、证据是数据、以及三条会变成噪声的判据（决策 95–107）

`tuoen doctor` 的风险不在"算错"，而在**说错**：把正常的东西报成坏的（用户立刻不再信任这个工具），
或者把"不知道"写成"没有"（用户据此做了一个错决定）。这一节记的是这两类风险各自的落点。

| # | 决策 | 结论 | 关键理由 |
|---|---|---|---|
| 95 | **事实与判断分开**：`collect_facts(ctx, opts) -> MachineFacts` 是唯一碰机器的地方（只读），`diagnose(&MachineFacts) -> Vec<Finding>` 是**纯函数** | 前四个事实字段就是 `capture` 的四个文件形状（`path.toml` / `env.toml` / `tools.toml` / `wsl.toml`），同一批采集器产出 | 买到三件事：① 检查项的测试不用造机器（票据要求"每个正例都必须有对应的反例"，纯函数让那件事变便宜）；② "`capture` 写下的"与"`doctor` 诊断的"不可能漂移；③ 检查项可以单独读。**没有第二条通往机器的路** —— 检查项里出现一次 `ctx.fs` 就说明这条分界破了 |
| 96 | **`FindingId` 是公开契约**：23 个 ID 写成 `ids` 模块里的常量 + 一张 `ids::ALL` 表，而不是让检查项自己拼字符串 | 有一条用例断言 `ALL` 无重复、恰好 23 个、四个前缀族齐全；`--json` 的消费者按 ID 忽略/聚焦 | 票据原话："每条发现的 ID 是公开契约，改动即为破坏性变更"。拼出来的字符串会在某次重构里悄悄改名，而列表里的常量改不动 |
| 97 | **`evidence` 是数据，`message` 是散文**：每条 evidence 是"位置/名字 + 值"（`machine#21`、`tool=java command=javac dir=…`），**不许出现中文句子** | 中文解释只进 `message`，而 `message` 是 `#[serde(skip)]`（不进 `--json`） | 这条是**当场被抓出来的**：`tool.ghost` 的第一版把检测引擎给**人**看的那句话（`path=<无 InstallLocation，卸载键 {…}>`）直接抄进了 evidence，于是 `doctor --json` 的成功载荷里出现中文 —— 而 CLI 侧那条"成功载荷无 CJK"的契约测试立刻红了。它与决策 35（`--json` 不本地化）和 `path_contract.rs` 的同名断言是同一件事 |
| 98 | **`confidence` 只在结论真的来自检测引擎的一行时才有值**（五个 `tool.*` 检查），其余检查不编一个 | 没有值时 `#[serde(skip_serializing_if)]` 不留键 | 票据把 `confidence` 列进了输出契约，但 `path.missing` 这类结论的确定性由**判据本身**表达（含 `%` 的条目**根本不判**失效，所以报出来的每一条都是确定的）。给它们编一个置信度只会让那个字段变成装饰 |
| 99 | **`path.length-budget` 的四档**：`ok` **不报**、`warning` info、`critical` warn、`exceeded` **error** | 8191 与 8192 的差别要说准：`<= 8191` 还能用（`critical`），`> 8191` 是 `cmd.exe` **整条 `PATH` 一次性全部失效** | 票据只写了"error（超限）/ info"，中间两档是补齐的。`ok` 不报是刻意的：**一条永远响的检查等于噪声**，而这条检查的反例就是"健康的机器"（票据要求每个正例都有反例） |

## 2. 平台硬约束（来自本机实测，非推断）

这些是**必须绕着走的地面事实**，实现时不得假设相反情况。

### 2.1 PATH

```
进程 PATH 顺序 = [进程注入项] ; HKLM Path ; HKCU Path
                    ↑ 实测首条为机器条目 → 用户级工具只能追加到尾部
                    → 在名字冲突上永远输给机器级条目 → 必须用 shim
```
- **机器 Path 与用户 Path 都实测不含 `%VAR%`**（HKLM 标了 `REG_EXPAND_SZ` 却零变量）
- **写 PATH 绝不用 `setx`**：文档写 1024 字符上限且**内容是"被裁剪后应用"**（静默数据丢失），且操作已存在的值会**永久展开所有 `%VAR%` 引用**。本机算术：用户 725 + 机器 978 = 1704 字符，`setx PATH "%PATH%;..."` 会**既裁剪又把整条机器 PATH 永久复制进 HKCU**
- **正确做法**（Scoop 源码同款）：直接写 `HKCU\Environment`，**值含 `%` 才用 `REG_EXPAND_SZ`，否则保留原类型，再否则 `REG_SZ`**；读取用 `DoNotExpandEnvironmentNames`；随后广播
  `SendMessageTimeoutW(HWND_BROADCAST, WM_SETTINGCHANGE=0x1a, 0, L"Environment", SMTO_ABORTIFHUNG=2, 5000, &out)`
- **两个不同的悬崖**：`setx` 截断 1024 字符；**`cmd.exe` 在 8191 字符后完全忽略 `Path`**——超过后**整条 PATH 一次性全部失效**，所有命令都报"不是内部或外部命令"。必须做**长度预算告警**
- **变更可见性**：环境块在 `CreateProcess` 时复制，**只有 Explorer 及其之后新起的子进程**能拿到；已在运行的 cmd/PowerShell/VS Code/IDE/服务/计划任务都拿不到，我们自己的进程也拿不到（除非显式打补丁）。"请重启终端"是平台限制，不是工具不友好
- **换机失效**：本机 11 条 PATH 硬编码了用户名（其中 **2 条在机器级**）。换账号名后静默失效，而 `Test-Path` 在本机仍通过 → **朴素校验器抓不到，必须显式检测用户名依赖**

### 2.2 文件系统与 reparse point

- **symlink**：Developer Mode 关闭 + 未提权时**文件与目录都创建失败**；`0x2` flag 无效
- **Junction**：免管理员可用；**但目标名可能嵌安装序号**（本机 Oracle 的 `java8path_target_1783390`），不可预测，必须记录目标而非猜测
- **硬链接**：仅 NTFS、仅文件、必须同卷；且当应用用 rename 替换自己的文件时会断（aqua 因此选硬链接，需注意此限制）
- **App Execution Aliases**：`...\WindowsApps\{python.exe, python3.exe, winget.exe, wsl.exe}` 是 reparse tag `0x8000001b`、长度 0 的别名，**既不是文件也不是符号链接**——基于复制的捕获什么也拿不到，而 `Test-Path` 式检查会通过，`Get-Command python` **成功但返回 0 字节幽灵**
- **长路径**：需要 `LongPathsEnabled=1` **且** 程序清单含 `<ws2:longPathAware>true</ws2:longPathAware>`。**相对路径永远受 MAX_PATH 限制**（`\\?\` 无法加前缀，实测约 300 字符的相对路径失败）→ 自己的解压/重命名代码加 `\\?\` 前缀，**并把 shell 集成视为永久 260 字符受限**
- **PATH 上的空格**：本机 48 条中 14 条含空格（29%），最糟的是 `C:\Dev\IDE\IDEA26\IntelliJ IDEA 2026.1.1\bin`（**同时含空格和版本号**）→ 不加引号的 shim 设计会当场崩

### 2.3 归档格式

- **系统自带 `tar.exe` 是 bsdtar 3.8.8 / libarchive 3.8.8**（含 libzstd 1.5.7 + liblzma 5.8.1）→ `.zip` / `.tar.gz` / `.tar.xz` / `.tar.zst` / `.tar.bz2` 可靠 shellout 解决
- ~~**`.7z` 是唯一缺口**，需要内置库~~ —— **实测推翻了这一条（决策 44）**：
  libarchive 3.8.8 自己就认 7z。拿阿里镜像那份真的
  `node-v24.19.0-win-x64.7z`（23,441,591 字节，哈希与上游一致）实测：
  `tar.exe -tf` 列出 2454 个条目、`-xf` 解出的 `node.exe` 能跑并报 `v24.19.0`。
  **不需要内置任何 7z 库。**

### 2.4 区域与编码

- 本机 zh-CN，**PowerShell 的符号链接报错是本地化的**（`此操作需要管理员权限。`）→ **永远不要匹配错误文本，要匹配 HResult / Win32 码**
- `git --version` / `java -version` 输出到 **stderr**，`node -v` 到 **stdout** → 版本探测必须同时读两路

### 2.5 安全

- **Zip Slip 在这个威胁模型里仍然活跃**（CVE-2026-27800 Zed `extract_zip` 缺 `../` 校验；CVE-2026-28486 安装命令期间的路径穿越）。解压检查清单：先规范化再断言在根目录内、拒绝绝对路径/UNC/`..`、校验 **symlink 条目目标**、拒绝保留设备名（`CON`/`PRN`/`AUX`/`NUL`/`COM1-9`/`LPT1-9`）、拒绝结尾点和空格、拒绝名字里的 `:`（ADS 写原语）、大小写碰撞检测、大小/条目数上限
- **MSVC / VS Build Tools 不是包**：微软文档说 `--quiet` "对标准用户不可编程使用"、安装操作"需要管理员权限"、且**不可再分发** → **建模为带外管理员前置条件，唯一正确做法是以管理员调用微软自己的 bootstrapper + `.vsconfig`**

## 3. 许可与再分发（产品级约束，不是法务脚注）
